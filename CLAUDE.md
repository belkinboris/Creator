# Создатель — CLAUDE.md

## Проект

**Создатель** (projectsozdatel.ru) — сервис проверки бизнес-идей.
Путь пользователя: бесплатная проверка спроса → платный живой тест.

**Стек:** FastAPI + SQLModel + PostgreSQL, Python 3.12
**Запуск:** `uvicorn app.main:app --host 0.0.0.0 --port 8080`
**Healthcheck:** `GET /health` (лёгкий, без обращения к БД)
**Деплой:** GitHub → Timeweb Cloud. Автодеплой ненадёжен — после push владелец жмёт ▶ вручную в панели Timeweb.

## Шкала пути 0→6 (STAGE_NAMES, покупатель Создателя)

«Проверочная страница» и «Реклама» объединены в «Тест на реальных людях» —
по кастдев-фидбеку это один платный этап с точки зрения покупателя (мы
собираем страницу, он по нашей инструкции запускает рекламу), раздельная
нумерация только путала. Копии этого списка живут в `app/main.py` и
`app/report_engine.py` — держать в синхроне вручную (см. тест
`TestStageMerge.test_report_engine_stage_names_match_merged_scale`).

| # | Этап |
|---|------|
| 0 | Идея |
| 1 | Спрос |
| 2 | Тест на реальных людях |
| 3 | Заявки |
| 4 | Первые продажи |
| 5 | Повторяемость |
| 6 | Удержание |

**Не путать с `TRACKED_STAGE_NAMES`** (`app/main.py`) — отдельная, сознательно
не объединённая шкала из 8 названий для `TrackedProject` (внешние проекты
владельца вне Создателя, например АвтоПост, видны в `/desk` как виджет
портфеля). У неё своя, более старая нумерация (0 Идея … 7 Удержание,
с «Проверочная страница»/«Реклама» раздельно) — `TrackedProject.stage` это
сырое целое число, уже сохранённое в БД для существующих записей; смени эту
шкалу вместе с покупательской — и старые записи начнут указывать не на те
этапы (а `stage=7` упадёт по `IndexError` на укороченном массиве). Общий
язык с воронкой Создателя внешнему проекту не нужен.

на весь сайт («Заявки на живой тест» и т.п.) — отдельная задача, не делать
походя.

## Архитектурные детали

- Приложение — единый FastAPI-процесс, без фоновых воркеров и очередей.
- Все вызовы LLM — `async` через `httpx.AsyncClient`.
- Вердикт (`compute_verdict`) — детерминированная логика, без LLM.
- Общий балл идеи (`check_demand` в `app/demand.py`) — спрос из Вордстата
  выступает воротами, а не рядовой 1/4 средней: `overall = min(среднее по
  4 шкалам, балл спроса)`. Иначе почти нулевая частотность тонет в трёх
  хороших LLM-шкалах (конкуренция/своевременность/реализуемость) и идея
  показывает обманчиво высокий общий балл при отсутствии реального спроса.
- Rate-limit: 30 событий / 60 сек на IP, in-memory.
- Аутентификация владельца: заголовок `X-Owner-Key` или query-параметр `key`.
- Адрес страниц результата и отчёта — **неугадываемый** `DemandCheck.public_id`,
  а не порядковый номер: иначе чужая идея читается перебором 42 → 41, причём
  и на `/r/`, и в тизере `/report/` (E6). Ссылкой на результат делятся
  намеренно, поэтому вход не требуем — закрыта только угадываемость. Номер
  записи остался внутри API; порядковый номер в адресе принимается только у
  владельца по ключу или хозяина проверки по сессии и отдаёт редирект на
  канонический адрес с сохранением query (`_find_check` в `app/main.py`).
- `/p/{idea_id}` (страница проекта) открыта и из `/desk` (владелец), и из
  `/account` (покупатель) — `/api/verdict/{id}` и `/api/series/{id}` поэтому
  принимают ЛИБО ключ владельца, ЛИБО сессию кабинета, если
  `SmokeProject.contact` совпадает с контактом сессии (`_project_access_ok`
  в `app/main.py`). Просто `_check_owner` здесь недостаточно — покупатель не
  знает и не должен знать секретный ключ владельца.
- БД по умолчанию: SQLite (dev) / PostgreSQL (production, `DATABASE_URL`).
- Частотность Вордстата — ОДИН путь (см. `app/demand.py`): прокси внутри
  Yandex Cloud Search API v2 (`YANDEX_API_KEY`/`YANDEX_FOLDER_ID`,
  сервисный аккаунт с ролью `search-api.webSearch.user`). **Общедоступен
  с 18 мая 2026** (вышел из preview), без одобрения Яндекса. Старый
  «Wordstat API» (`api.wordstat.yandex.net`, Bearer OAuth-токен из
  приложения на oauth.yandex.ru) — проверенный факт, действительно
  ОТДЕЛЬНЫЙ от Cloud Search API продукт (не синоним), но подключается
  только через заявку в поддержку Яндекс.Директа с ClientId — не
  self-service, даже если под рукой уже есть OAuth-клиент, совмещённый
  с Директом (было отдельно проверено на владельческом случае 2026-08-02).
  Раз рабочий self-service путь уже есть — код под старый путь сознательно
  не реализован. При жалобе «нет данных» — сначала
  `GET /api/diag/yandex?key=...` (owner-only): покажет сырой ответ вместо
  гадания.
- Формулировок проверяем ШЕСТЬ (`FORMULATIONS_COUNT`), а не три, и промпт
  требует три разных ТИПА запроса: услуга / широкая категория / описание
  задачи своими словами. Кастдев 2026-08-02: тройка давала максимум 941/мес,
  а реальный массовый запрос той же темы — 3984/мес, просто в неё не попал.
  Дело не в конкретном слове-приставке (у каждой ниши своё), а в размере и
  разнообразии выборки — не «чинить» это добавлением частных слов в промпт.
  Запросы уходят в Вордстат параллельно (`asyncio.gather` в `check_demand`),
  поэтому шесть ждутся примерно столько же, сколько три; строки на выдаче
  отсортированы по частотности.
- `count=0` и `count=None` — РАЗНОЕ и склеивать их нельзя. Ноль означает
  «Вордстат ответил, таких запросов нет» → на экране «не ищут»; None —
  «Вордстат не ответил» (нет ключей, сеть, квота) → «не удалось измерить»
  и вердикт `unknown`. Раньше оба давали None, и честно измеренный ноль
  показывался как поломка сервиса.
- Блок конкурентов показывает только БИЗНЕСЫ: `_is_not_competitor`
  (`app/demand.py`) отсеивает энциклопедии, СМИ, форумы, соцсети и
  госресурсы — иначе в «конкурентах» оказываются Википедия и Лента (кастдев
  2026-08-02). Сверка идёт по базовому домену ЦЕЛИКОМ, не по вхождению
  подстроки: «t.me» живёт внутри коммерческого `market.merch.ru`. Если после
  фильтра не осталось никого — это находка («по запросу читают, а не
  покупают»), а не пустой блок.
- Частотность одной LLM-угаданной формулировки может сильно занизить спрос
  на свежие/жаргонные ниши (кастдев: «создание рекламного видео» — 157/мес,
  реальный ходовой запрос для той же идеи «нейросеть для рекламы» — 902/мес).
  Cloud Search API путь возвращает вместе с `totalCount` список похожих
  формулировок (`topRequests: [{"phrase", "count"}]`) — `wordstat_best`
  берёт максимум по ним, а не только дословно запрошенную фразу (см.
  `_best_related`). Имя поля запроса `numPhrases`/`num_phrases` не
  подтверждено официальной докой (недоступна для чтения) — шлём оба
  варианта написания, не полагаясь на одно. Если Вордстат подсказал более
  популярную формулировку, чем угадала LLM, `check_demand` не подменяет
  молча отображаемую фразу её счётом (иначе ручная проверка исходной фразы
  в Вордстате покажет другое число) — кладёт находку в отдельное поле
  `matched_phrase`, `result.html` показывает её припиской под исходной.
- Платный отчёт имеет ДВЕ оптики (`PURPOSES` в `app/report_engine.py`),
  `DemandCheck.purpose` протянут от лендинга до генерации:
  `business` — фаундер, персона «аналитик венчурного фонда», план запуска по
  этапам Создателя; `social_contract` — человек готовит обоснование для
  комиссии соцзащиты под выплату ~350к (лендинг `/social-contract`), персона
  «экономист», обязательная смета расходов + план доходов + окупаемость,
  план запуска про регистрацию статуса и отчётность перед соцзащитой.
  Венчурные критерии для второй аудитории вредны: «не масштабируется» даёт
  низкий балл там, где устойчивый доход семьи и есть цель.
  Промпт НЕ должен разрешать модели отказаться считать («мало данных») —
  расчёт это то, за что заплатили; при нехватке вводных модель обязана
  принять явные допущения и назвать их (см. `_FINANCE_SPEC`).
  Секции `finance` нет в `QUICK_KEYS` — тариф за 990 ₽ идёт без сметы, и
  витрина обязана говорить об этом прямо.
  **19 из 21 раздела `SECTION_SPECS` несут `by_audience["social_contract"]`**
  (решение владельца 2026-08-02, закрывает D1): не переделывать разделы под
  каждую аудиторию по отдельности, но структура полного бизнес-плана для
  соцконтракта обязана отвечать на то, что реально спрашивает комиссия, а не
  читаться венчурным разбором с заменённым названием. Без override остались
  сознательно только `market` (цифры Вордстата от аудитории не зависят) и
  `verdict` (решение «запускать/дорабатывать/нет» одинаково по смыслу для
  обеих оптик). Это НЕ выверенная по номеру статьи цитата закона — точные
  требования к форме устанавливает региональное положение и могут отличаться
  по регионам; сделано по общепринятой структуре федеральной методики
  Минтруда (смета в рамках лимита, план доходов и окупаемость, статус
  самозанятости/ИП, отчётность). Обычный бизнес-план (business, student)
  этой правкой не тронут — остаётся венчурным, как было.
- ЮКасса требует чек (54-ФЗ) с `customer.email`/`customer.phone` — контакт
  из формы обязан быть почтой/телефоном для платных заказов (см.
  `payments.valid_receipt_contact`); телеграм-хэндл проходит только в
  заявку без оплаты (без настроенной кассы).
- Личный кабинет покупателя (`/account`) — вход по magic-link на почту, без
  пароля (`app/mailer.py`, SMTP reg.ru Mail-1). **Сам вход происходит на
  `POST /account/verify`, а GET по ссылке из письма только показывает
  страницу с кнопкой** (`static/verify.html`) и токен не гасит: почтовые
  провайдеры и антивирусы открывают ссылки из писем сами, до человека, и
  одноразовый токен сгорал раньше, чем адресат успевал кликнуть — вплоть до
  полной невозможности войти (A15). Токен передаётся в query действия формы,
  а не полем: разбор тела формы потребовал бы `python-multipart`. Нужны env:
  `SOZDATEL_SMTP_HOST`, `SOZDATEL_SMTP_PORT`, `SOZDATEL_SMTP_USER`,
  `SOZDATEL_SMTP_PASSWORD`. Порт решает способ шифрования: 465 — SSL с
  первого байта, любой другой (обычно 587) — STARTTLS, см. `_transmit`.
  Отдельно `SOZDATEL_OWNER_EMAIL` — куда писать
  владельцу об оплате, доставка которой сорвалась (`mailer.notify_owner`,
  никогда не бросает исключение). Не задана — уведомления молча не уходят.
  **Почта — единственная подсистема, которая ломается молча**, поэтому у
  неё есть свой прибор: блок «Почта» в `/desk` и ручка
  `GET /api/diag/mail?key=...&to=...` (owner-only, `mailer.diagnose`) —
  показывает, чего не хватает, и по кнопке шлёт проверочное письмо, называя
  причину отказа человеческими словами. Пароль не возвращается никогда.
  `SmokeProject.contact` не проставляется
  автоматически — владелец привязывает вручную через
  `PATCH /api/projects/{idea_id}/contact` при запуске проекта под оплаченную
  заявку живого теста.
- Бесплатная проверка спроса (`DemandCheck`) не привязана к контакту, пока
  человек сам не привяжет её (`POST /api/demand/{id}/save`, кнопка
  «Сохранить в кабинете» на `/r/`) — иначе результат, полученный без прямой
  ссылки на `/account`, негде найти повторно. Уже вошедшему в кабинет
  привязка идёт мгновенно контактом сессии; для остальных — email + тот же
  magic-link, что у обычного входа (`_send_magic_link` в `app/main.py`,
  общая часть с `/api/account/request-link`). Если проверку делает уже
  вошедший — `/api/demand` сам проставляет контакт при создании, без
  отдельного шага.

## Рабочий цикл

0. **Начни с `PRODUCT_ROADMAP.md`** — это источник правды: принципы (не
   обсуждаются), приоритизированный бэклог и журнал работ. Задачи берутся
   оттуда сверху вниз, блок A всегда вперёд остальных. В конце сессии —
   дописать журнал и обновить статус задачи. Файл нужен потому, что каждая
   автономная сессия начинается с чистого листа: без него работа расползается.
1. **Любое изменение — с тестами.** Добавляешь или меняешь поведение — покрой тестом.
2. **Запускай `python -m pytest tests/` после каждого изменения.** Все тесты должны быть зелёными до сдачи.
2a. **Страницу, которую целиком собирает скрипт (`/r/`, `/report/`), нельзя
   проверить подстроками в HTML.** Обжигались дважды: удалённый элемент
   (`#path-next-text`), в который остались присваивания, ронял скрипт — и
   правило `.step:not(.active):not(.done){display:none}` скрывало ВСЮ ленту.
   Код ответа 200, все подстроки на месте, страница пустая, и только на
   части вердиктов. Такие правки проверять браузером

## Известные проблемы (честно, на 2026-08-02)

Подробности и приоритеты — в `PRODUCT_ROADMAP.md`. Коротко, чтобы не
обнаружить это заново на боевом трафике:

- **Примера отчёта не существует** — платят, не видя, что получат. Механизм
  готов и ждёт одного действия владельца: собрать отчёт владельческим
  прогоном (`/report/{public_id}?key=...&preview=full`), затем
  `POST /api/example/publish?check_id=...&tier=full&key=...`. Пока примера
  нет, ссылка «Посмотреть пример» на витринах не показывается вовсе
  (`_example_link`) — звать на пустую страницу хуже, чем не звать.
- **Качество платного отчёта не проверялось на живой модели** — в dev нет
  LLM-ключей, промпты правились по тексту промпта, а не по результату.
  Промпт теперь ЯВНО сообщает модели, что читатель уже видел бесплатную
  проверку, и запрещает пересказ (`_ALREADY_SEEN` в `app/report_engine.py`)
  — но подействовало ли это на живой текст, не проверено.
- **В `dev` окружении нет ключей Яндекса/ЮКассы/SMTP** — эти пути
  проверяются только инъекцией `_post`/`monkeypatch` в тестах.
- `static/portfolio.html` — мёртвый файл со старой шкалой этапов, роут
  `/portfolio` редиректит на `/desk`.
